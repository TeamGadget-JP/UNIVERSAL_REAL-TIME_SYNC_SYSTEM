# URSS 바이브 코딩 실전 가이드

## AI와 함께 나만의 Endpoint와 제작 워크플로를 만들어 보세요

**Built with AI. Grown by Creators.**

URSS는 제공되는 기능을 사용하는 데 그치지 않고, 크리에이터가 직접 Endpoint를 수정하거나 새로운 Endpoint를 개발할 수 있는 플랫폼입니다.

이 가이드에서는 TeamGadget이 GEC에서 URSS로 개발을 이어 오면서 실제로 활용한 AI 협업 개발 방식을 소개합니다. 프로그래밍 경험이 적은 분도 도전할 수 있도록 전문적인 코딩 기술보다는 **사양을 정하고, AI와 정보를 공유하고, 실제로 실행해 확인하는 과정**을 중심으로 정리했습니다.

이 방법으로 누구나 같은 결과를 얻을 수 있다고 보장하는 것은 아닙니다. 하나의 실전 사례로 참고하고, 자신의 환경에 맞는 부분을 활용해 보세요.

### 이 가이드의 개발 환경

TeamGadget이 실제로 사용하는 환경을 기준으로 작성했습니다.

- **AI:** ChatGPT (GPT-5.6 Sol)
- **구독 플랜:** ChatGPT Plus
- **추론 설정:** 사용 가능한 최고 수준
- **진행 방식:** 전용 채팅에서 AI와 논의하고 코드 작성·수정을 요청한 뒤, 실제 환경에서 검증
- **대상:** URSS의 기존 Endpoint 수정, 새로운 기능 추가, 신규 Endpoint 개발

동일한 모델이나 구독 플랜이 반드시 필요한 것은 아닙니다. 또한 Visual Studio 같은 코드 편집기가 있으면 편리하지만 필수는 아닙니다. AI가 작성한 파일을 다운로드하고, 원본을 백업한 다음 파일을 교체해 확인하는 방식으로도 개발을 진행할 수 있습니다.

## Step 1: 개발 전용 채팅을 만든다

먼저 개발 대상별로 전용 채팅(스레드)을 만듭니다.

**핵심은 그 채팅에서는 개발 이외의 이야기를 하지 않는 것입니다.**

개발 채팅에는 사양, 설계 결정, 구현 현황, 오류 로그, 수정 이력 등이 차곡차곡 쌓입니다. 관련 없는 주제를 섞지 않으면 무엇을 결정했고 무엇을 확인했는지 나중에 되짚어 보기 쉬워집니다.

장기 개발로 인해 새 스레드로 옮겨야 한다면, 확정된 사양, 완료한 개발 단계, 미해결 문제, 다음 작업을 인수인계 문서로 정리해 달라고 AI에 요청하면 편리합니다.

## Step 2: 개발 자료와 대상 소스 코드를 AI에 공유한다

코드를 작성하기 전에 먼저 AI가 기존 시스템을 이해하도록 합니다.

URSS Endpoint 개발이라면 기본적으로 다음 정보를 공유합니다.

- **G-HUB의 Endpoint 개발 자료**(통신 사양, 연결 규칙 등)
- **개발 대상 Endpoint의 소스 코드**
- 필요한 설정 파일, 대상 애플리케이션 버전, 현재 동작 상태

자료를 전달한 뒤에는 AI에게 코드 구조, 처리 흐름, 변경이 필요할 것으로 보이는 부분을 정리해 달라고 요청하세요. **이 단계에서는 아직 코딩을 시작하지 않습니다.**

URSS에서는 배포된 G-HUB 애플리케이션과 개발 자료를 이용하는 것을 전제로 합니다. 공개된 Endpoint 소스를 다룰 때도 각 파일의 라이선스, 수정·재배포 조건, 비공개 컴포넌트의 경계를 지켜 주세요.

## Step 3: 바로 코딩하지 말고 사양부터 정한다

**이 단계는 특히 중요합니다.**

구현하고 싶은 기능을 AI에 설명하고, 구현 방법과 기존 기능에 미치는 영향, 예상되는 문제점을 함께 논의합니다. 원하는 바를 충분히 전달하면서 AI에게도 대안과 우려 사항을 제안하도록 하여, 함께 사양을 정리합니다.

처음부터 명확히 해 두어야 할 원칙은 다음과 같습니다.

> **현재 안정적으로 동작하는 부분은 원칙적으로 변경하거나 망가뜨리지 않는다. 필요한 수정 범위를 제한하고 기존 기능과의 호환성을 유지한다.**

새로운 기능이 작동하더라도 기존에 잘 쓰던 기능이 망가지면 의미가 없습니다. 사양을 정할 때부터 '변경해도 되는 부분'과 '반드시 유지해야 하는 부분'을 구분해 두세요.

## Step 4: 개발 단계를 나누고 AI와 공유한다

사양이 확정되면 AI에게 구현 작업을 여러 개발 단계로 나눠 달라고 요청합니다.

예를 들어 내부 처리 추가, 연결 부분 구현, UI 변경, 기능별 테스트 등으로 구분할 수 있습니다. 각 단계에서 **무엇을 하고, 무엇이 확인되면 완료로 판단할지** 정해 두면 현재 진행 상황을 파악하기 쉬워집니다.

AI가 제안한 계획을 그대로 받아들일 필요는 없습니다. 작업 순서와 범위를 검토하고, 납득할 수 있는 계획을 만든 뒤 코딩을 시작합니다.

## Step 5: 코딩을 시작한다

이제 AI에게 코드 작성과 수정을 요청합니다. TeamGadget은 다음 과정을 반복하며 개발했습니다.

1. AI에게 해당 단계에 필요한 파일을 작성하거나 수정해 달라고 요청한다.
2. 작성된 파일을 다운로드한다.
3. **원본 파일은 반드시 백업한다.**
4. 대상 파일을 교체한다.
5. 실제 애플리케이션에서 동작을 확인한다.
6. 결과를 AI에 보고하고, 필요한 경우에만 다음 수정으로 넘어간다.

파일을 직접 편집할 수 있는 환경이라면 코드 편집기를 사용해도 괜찮습니다. 중요한 것은 **무엇을 변경했는지 파악하고, 문제가 발생했을 때 이전 상태로 되돌릴 수 있도록 하는 것**입니다.

### 중요: AI와는 최대한 자세하게 정보를 공유하세요

바이브 코딩에서는 **정보 공유가 정말 중요합니다.**

AI는 사용자가 알려 주지 않은 PC 화면의 상태나 조작 결과를 저절로 알 수 없습니다. 오류가 났을 때 단순히 '작동하지 않아요'라고만 하지 말고, **어떤 조작을 했는지, 실제로 무엇이 일어났는지, 원래는 어떻게 동작해야 했는지** 구체적으로 설명하세요.

- 오류 메시지와 로그는 가능한 한 생략하지 않고 공유한다.
- 문제가 발생하기까지의 조작 순서, 발생 시점, 재현 조건을 설명한다.
- 관련 화면과 설정, 조작 전후의 상태를 **스크린샷으로 첨부한다.**
- 오류 메시지가 없어도 '이전보다 반응이 느리다', '조작감이 달라졌다' 같은 이상 징후를 구체적으로 보고한다.
- **직접 확인한 사실과 자신의 추측을 구분한다.** 원인을 억지로 단정할 필요는 없다.

특히 스크린샷은 매우 유용합니다. 글로만 설명하기 어려운 버튼 상태, 화면 배치, 오류가 표시된 위치 등을 한꺼번에 전달할 수 있습니다.

**Windows에서 스크린샷을 채팅에 붙여 넣는 방법**

1. `Windows 키 + Shift + S`를 누른다.
2. 필요한 화면 영역을 선택한다.
3. 채팅 입력창에서 `Ctrl + V`를 눌러 붙여 넣는다.
4. 상황을 설명하는 글을 덧붙여 전송한다.

예를 들어 다음과 같이 보고하면 상황을 더 쉽게 파악할 수 있습니다.

> 연결 버튼을 눌러도 표시가 'WAIT' 상태에서 바뀌지 않습니다. G-HUB에는 연결 로그가 나타나지만 캐릭터는 움직이지 않습니다. 조작 직후의 화면과 로그를 첨부합니다. 기대한 동작은 연결 후 캐릭터의 포즈가 동기화되는 것입니다.

**이상이 발생했다는 사실 자체를 AI가 추측하게 만들지 마세요.** 판단에 필요한 정보를 최대한 많이 전달하고, 그 정보를 바탕으로 원인을 분석하도록 도움을 받으세요.

※ 로그나 이미지를 공유하기 전에는 비밀번호, 토큰, 개인정보 등이 포함되어 있지 않은지 확인하세요.

## Step 6: 새로운 문제나 아이디어가 생기면 일단 코딩을 멈춘다

**이 단계 역시 매우 중요합니다.**

개발 중에는 예상하지 못한 문제가 발견되거나 새로운 아이디어가 떠오르기도 합니다. 그때마다 흐름에 따라 수정을 계속 추가하면 왜 변경했는지, 어디까지 영향을 미치는지 파악하기 어려워집니다.

그럴 때는 **일단 코딩을 중단합니다.**

AI와 상의하여 기존 사양을 변경할지, 다른 방법을 채택할지, 이번에는 보류할지를 결정하세요. 사양이 바뀌었다면 개발 단계도 갱신하고, 변경된 방향을 공유한 다음 다시 시작합니다.

> **아이디어는 병렬로, 개발은 순차적으로.**

아이디어는 자유롭게 떠올려도 괜찮습니다. 다만 구현은 사양을 정리한 뒤 순서대로 진행합니다.

## Step 7: 동작 테스트와 디버깅을 진행한다

구현이 어느 정도 끝나면 기능별 동작 테스트로 넘어갑니다.

새로운 기능뿐 아니라 **기존 기능이 망가지지 않았는지**도 반드시 확인합니다. 연결·연결 해제, 재시작, 설정 저장·복원, 여러 캐릭터 사용 등 대상 기능에 맞는 실제 사용 조건도 시험해 보세요.

문제가 발견되면 Step 5와 마찬가지로 조작 순서, 로그, 스크린샷, 기대한 결과와 실제 결과를 공유합니다. 수정한 뒤에는 문제가 해결되었는지뿐 아니라 다른 부분에 영향이 없는지도 확인합니다.

**코드 작성이 끝났다는 것과 정상 동작이 검증되었다는 것은 다릅니다.**

## Step 8: 도그푸딩(실사용 내구 테스트)

기본 테스트를 마쳤다면 평소 제작 작업에서 실제로 계속 사용해 보세요. 이를 도그푸딩(Dogfooding)이라고 합니다.

**이 단계부터는 사용자 자신이 주역입니다.**

기능이 일단 작동하는지에 그치지 않고, 계속 사용해도 안정적인지, 조작하기 편한지, 제작 작업을 방해하지 않는지 확인합니다.

이 기간에는 불편한 점을 발견하더라도 **원칙적으로 즉시 코드를 수정하지 않고 먼저 기록에 집중하는 방식**을 권합니다. 작은 버그, 조작상의 불편함, 개선 아이디어 등을 모았다가 적절한 시점에 함께 사양을 재검토합니다.

수정과 평가를 자주 뒤섞지 않으면 같은 상태의 소프트웨어를 차분하게 시험할 수 있습니다.

## Step 9: 개발 완료 후 공개 여부를 결정한다

테스트와 도그푸딩을 마치고 문제가 없다면 개발 완료입니다.

완성된 Endpoint는 **혼자 사용해도 좋고, 커뮤니티에 공개해도 좋습니다.**

공개한다면 GitHub에서 Fork하여 자신만의 확장판으로 배포하는 방법이 있습니다. 변경 사항, 지원 버전, 설치 방법, 알려진 제한 사항을 README에 적어 두면 다른 사용자도 활용 여부를 판단하기 쉬워집니다.

공개하기 전에는 소스 코드와 포함된 파일의 라이선스, 재배포 조건, 비공개 컴포넌트의 취급 방식을 반드시 확인하세요. **직접 수정할 수 있다는 것과 모든 파일을 재배포할 수 있다는 것은 다릅니다.**

## 실전 사례: TeamGadget은 AI와의 공동 개발로 어디까지 만들었을까?

마지막으로, 이 가이드의 바탕이 된 URSS의 개발 실적을 소개합니다.

AI를 사용하면 누구나 같은 규모의 시스템을 완성할 수 있다는 보장은 아닙니다. **프로그래밍에 대한 전문 지식이 거의 없는 상태에서 AI와 협력하여 어디까지 도달했는지** 보여 주는 하나의 사례입니다.

### 개발 규모와 기간

| 항목 | TeamGadget의 실제 사례 |
| --- | --- |
| 개발 방식 | ChatGPT와의 대화를 통한 바이브 코딩 |
| 사용 환경 | ChatGPT Plus / GPT-5.6 Sol / 최고 수준의 추론 설정 |
| URSS 개발 기간 | 약 2.5개월 |
| 전신인 GEC 시절부터의 누적 기간 | 약 6개월 |
| 소스 코드 규모 | **약 46,000줄**(전체 개발 규모의 추정치) |
| 개발 대상 | G-HUB, GHEC, GHEU, GHEB, GHEG, ShapeMixer Entangle |

※ 코드 줄 수는 개발 규모를 알리기 위한 대략적인 수치입니다. 코드 줄 수만으로 소프트웨어의 품질이나 개발자의 역량을 평가하는 것은 아닙니다.

### 구현·검증한 기능

개발한 컴포넌트를 조합하여 다음과 같은 워크플로를 구현하고 검증했습니다.

- Cascadeur와 Unity·Blender·Godot 간의 실시간 Body 동기화
- ShapeMixer Entangle과 연계한 Facial / Shape Key 동기화
- G-HUB의 공통 타임라인과 양방향 타임라인 동기화
- 애니메이션 오프라인 베이크 및 대응 제작 애플리케이션으로의 전달
- 최대 5개 캐릭터의 동기화 및 검증
- 개발자가 기존 Endpoint를 확장하고 새로운 Endpoint 개발에도 도전할 수 있는 기반

단순한 코드 생성 실험에 그치지 않고, 실제 애플리케이션에서 반복적으로 동작을 확인하여 배포 가능한 소프트웨어로 공개하는 단계까지 진행했습니다.

### 사람과 AI의 공동 작업에서 맡은 역할

**TeamGadget(사람)이 주로 담당한 일**

- 구현하고 싶은 기능과 워크플로의 구상
- 사양·우선순위·채택할 설계에 대한 최종 결정
- 기존의 안정적인 동작을 보호하기 위한 조건 설정

**AI 에이전트가 주로 담당한 일**

- 기술적 구현 방법과 설계안 검토·제안
- 코드 작성·수정
- 로그와 동작 보고를 바탕으로 한 원인 분석 및 수정안 제시
- 개발 단계와 작업 순서 정리
- 기술 자료, README 등 문서 작성 지원

이 역할 분담은 고정된 규칙이 아니라 TeamGadget이 실제로 작업한 방식입니다. 서로 논의하고 판단하는 과정을 반복하며 개발을 진행했습니다.

중요한 것은 **AI가 코드를 작성했다고 해서 완성품이 자동으로 만들어진 것은 아니라는 점**입니다. 사양 재검토, 실패한 구현, 반복적인 디버깅, 실제 사용을 통한 검증이 필요했습니다.

AI는 공유받지 못한 화면 너머의 상황을 알 수 없습니다. 사람이 사실을 관찰해 정확히 전달하고, AI가 그 정보를 바탕으로 기술적인 해결책을 생각하는 것. 이러한 협업이 개발을 진전시키는 데 중요한 역할을 했습니다.

### 이 사례를 통해 전하고 싶은 것

프로그래밍 지식이 적더라도 **무엇을 만들고 싶은지 생각하는 능력, 결과를 관찰하는 능력, 정보를 전달하는 능력, 최종적으로 판단하는 능력**은 개발에 크게 기여할 수 있습니다.

처음부터 대규모 Endpoint를 만들 필요는 없습니다. 기존 Endpoint에 자신이 원하는 기능 하나를 추가하는 것부터 시작해도 괜찮습니다.

**사양을 정한다. 작게 구현한다. 정확하게 보고한다. 실제로 사용하며 확인한다.**

그 과정을 반복하다 보면 자신만의 제작 환경을 만들어 갈 수 있습니다.

URSS는 완성된 워크플로를 일방적으로 강요하기 위한 것이 아닙니다. **크리에이터 자신이 직접 만들 수 있는 자유를 제공하기 위한 플랫폼**입니다.
